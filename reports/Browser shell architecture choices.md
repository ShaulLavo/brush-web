# Choose shell contracts before tuning throughput

**Keep Brush and the current browser-worker design for one bounded architecture experiment.** First batch the Rust utility's output and remove the WASI filesystem's repeated allocation and accounting work. Improve just-bash through its supported APIs in the same experiment, including explicitly labeled partial state carry. The present results do not establish that Rust or WebAssembly is inherently slower. Two small writes per printed number do not justify a fork, but Brush's sequential pipeline scheduler is a real limitation if the product requires concurrent streaming pipelines. The decision should turn on persistent sessions, live input, interruption, bounded memory, and useful throughput, while retaining Ghostty, Remix 3, and browser-only execution ([current architecture](https://github.com/ShaulLavo/brush-web/blob/5749936352339bdc3705c6d887042f1443e73355/docs/architecture.md)).

## Correct the host boundary before changing engines

The benchmark `seq` implementation is our Rust utility. It writes and flushes every number. Rust's `BufWriter` can combine those writes before they reach WASI, so neither Brush nor the ABI requires a separate browser crossing for the number and its newline. Batching only after JavaScript receives `fd_write` cannot remove crossings already paid for. Preserve explicit flushes before blocking input and at completion, cancellation, and prompt transitions. A timer queued on the blocked shell worker cannot perform those flushes ([utility source](https://github.com/ShaulLavo/brush-web/blob/5749936352339bdc3705c6d887042f1443e73355/rust/brush-browser/src/utilities.rs#L230), [BufWriter contract](https://doc.rust-lang.org/std/io/struct.BufWriter.html)).

The chosen WASI shim also copies each write's bytes and grows files by allocating exactly the new size and copying the old contents. Repeated small appends therefore copy an expanding prefix. Our quota checks traverse live filesystem objects on each write. These are concrete host algorithms to correct before replacing the interpreter. Upgrading the shim alone does not establish a fix, since its inspected current implementation still resizes growing files ([pinned WASI writes](https://github.com/bjorn3/browser_wasi_shim/blob/4a55f2a519d0ddfa7e4609c42e0c9769c37c9ae8/src/wasi.ts#L540), [file storage](https://github.com/bjorn3/browser_wasi_shim/blob/4a55f2a519d0ddfa7e4609c42e0c9769c37c9ae8/src/fs_mem.ts#L45), [quota accounting](https://github.com/ShaulLavo/brush-web/blob/5749936352339bdc3705c6d887042f1443e73355/src/wasi-host.ts#L217), [current storage](https://github.com/bjorn3/browser_wasi_shim/blob/b068ec2c22d68581c48f2592f8cca1681bf71a98/src/fs_mem.ts#L135)).

Upstream `mapfile` reads one byte at a time. Safe buffering requires preserving descriptor positions across commands and cloned handles. A temporary `BufReader` that discards unread bytes can break the next `read`, so this is a targeted semantic change rather than a blanket optimization ([mapfile](https://github.com/reubeno/brush/blob/4cfba081f2f8bcda8150010a57203d020f14f0cc/brush-builtins/src/mapfile.rs#L118), [shared handles](https://github.com/reubeno/brush/blob/4cfba081f2f8bcda8150010a57203d020f14f0cc/brush-core/src/openfiles.rs#L107), [BufReader warning](https://doc.rust-lang.org/std/io/struct.BufReader.html)).

**Pipeline scheduling is the deeper boundary.** Brush's WASM `spawn_blocking` waits for a stage to finish before yielding its handle, and pipes collect output until another stage reads it. Blocking a producer when its pipe fills would prevent the consumer from starting. The local 1 MiB limit makes failure bounded, but does not create concurrent streaming. A WASI-host swap cannot repair that scheduler. A browser-specific execution contract becomes justified when larger pipelines, jobs, or child programs become required ([WASM tasks](https://github.com/reubeno/brush/blob/4cfba081f2f8bcda8150010a57203d020f14f0cc/brush-core/src/sys/wasm/tasks.rs), [pipes](https://github.com/reubeno/brush/blob/4cfba081f2f8bcda8150010a57203d020f14f0cc/brush-core/src/sys/wasm/pipes.rs), [local patch](https://github.com/ShaulLavo/brush-web/blob/5749936352339bdc3705c6d887042f1443e73355/patches/brush-browser.patch)).

## Give just-bash its best supported adapter

The stock public API creates isolated execution state and retains filesystem changes. It returns final scalar environment values, and the next `exec` accepts environment and cwd options. Carrying that result can preserve scalar values, ordinary `PWD`-based cwd, and alias data, because aliases are stored in scalar environment entries. That deserves a labeled comparison mode. It does not preserve functions, arrays, variable attributes, shell options, or prior exit status, and mutable `PWD` is not a reliable typed directory snapshot ([published API](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts#L698), [alias storage](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/commands/alias/alias.ts), [state definition](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/interpreter/types.ts)).

The research's Node-worker probe of the browser entry confirms those API semantics. It is **not browser performance evidence**. The stdin option accepts a fixed string. Output accumulates until execution finishes, and the logger reports completed results rather than live chunks. The inspected newer source retains those contracts ([input and result API](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts), [output accumulation](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/interpreter/interpreter.ts#L237), [current source](https://github.com/vercel-labs/just-bash/blob/3ebd1c291462bc6bad3c6df7ebfe563d8799bfd9/packages/just-bash/src/Bash.ts)).

Fair improvements include public custom commands, injected filesystem operations, trace events, and a verified broader browser command set. The published baseline and one pinned current-source candidate should remain distinguishable. Current source includes text-allocation improvements, but this research has not reproduced their performance benefit. Private state mutation or reconstruction of functions from command text would obscure the missing session API ([embedding options](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts), [browser exclusions](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/commands/browser-excluded.ts), [allocation change](https://github.com/vercel-labs/just-bash/commit/864dfe5d4b9cf0447c4eb2002193f2ab2008bd0e)).

## Borrow process contracts without importing an IDE

Wasmer's browser shell supplies a useful example of one persistent guest shell with live byte streams and resize handling. Its bounded pipes transport chunks and wake writers when capacity becomes available. v86 has both individual serial-byte events and chunked virtio-console events, demonstrating that output granularity is a transport choice. These patterns support batching and backpressure without changing our terminal renderer ([Wasmer shell](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/wasmer-sh/src/main.ts#L522), [bounded streams](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/rust/src/stream.rs#L21), [v86 adapters](https://github.com/copy/v86/blob/94faf3d6b19ecabc53a4010aaa24252fa6a162e2/src/browser/serial.js#L318)).

Their runtimes answer broader functional questions. Wasmer/WASIX supports compiled guest processes, WebVM runs unmodified Linux binaries through CPU and syscall emulation, and v86 supplies a whole guest machine. WebContainers exposes Node.js process streams. None is a demonstrated faster replacement for this Brush binary, whose custom browser imports need explicit integration. Runtime package sizes also exclude different guest payloads and cannot rank startup costs ([Wasmer guide](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/js/README.md), [WebVM model](https://github.com/leaningtech/webvm/blob/7cd36b8d5b32a7532b1af11585d0de26ad92a251/README.md), [v86 model](https://github.com/copy/v86/blob/94faf3d6b19ecabc53a4010aaa24252fa6a162e2/Readme.md), [WebContainers API](https://webcontainers.io/api), [our imports](https://github.com/ShaulLavo/brush-web/blob/5749936352339bdc3705c6d887042f1443e73355/rust/brush-browser/src/host.rs)).

The reusable interpreter in `mvdan/sh` is a narrower design reference. Its runner retains state across calls and accepts readers, writers, filesystem handlers, and command handlers. Its browser stdin implementation documents that context cancellation alone cannot unblock a pending read. A Go browser pilot would still need an interruptible input host and line editor. JSPI can suspend synchronous WASM at asynchronous imports, but does not preempt a tight computation or turn Brush's sequential stages into concurrent pipelines ([runner API](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/api.go#L1187), [browser input caveat](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/stdin_js.go), [JSPI contract](https://github.com/WebAssembly/js-promise-integration/blob/5b247b1026d2f438eefe51914a79f4218cbda9f9/proposals/js-promise-integration/Overview.md)).

## One fixed experiment should end tuning

Use the unchanged Brush build, one Brush candidate with bounded utility batching and corrected WASI storage/accounting, and just-bash's best public adapter. Include at most one separately pinned just-bash source candidate. Keep Ghostty, renderer settings, browser, machine, correctness fixtures, and memory limits consistent. Report stock execution and partial-state carry separately.

| Boundary | Fixed workload | Evidence that decides the question |
| --- | --- | --- |
| Worker execution | Checksummed arithmetic and substitutions at two predetermined sizes | Worker-local completion time, excluding terminal rendering |
| Host I/O | 5,000 and 10,000 lines through files and the existing pipeline fixture | Import counts, bytes, host time, observed allocations, and verified contents |
| Presentation | Fixed transcript replay with matched chunk schedules, then each engine's natural output | Input-to-submitted-frame latency, first output, completion, and maximum queued bytes |
| Session behavior | Repeated commands, live input, resize, sleep, and tight-loop interruption | State and prompt survive; unsupported behavior is recorded as failure |

After one warmup, collect 30 warm samples per selected timing case, alternate engine order, and freeze artifacts. Distinguish observed counters from estimated copy volume. The existing roughly 47 ms arithmetic/substitution floor includes transport and browser polling, so it cannot rank interpreter CPU speed. Report hardware WebGPU and Canvas2D runs separately ([existing method and limits](https://github.com/ShaulLavo/brush-web/blob/5749936352339bdc3705c6d887042f1443e73355/docs/commands.md), [frame measurement limits](https://github.com/ShaulLavo/brush-web/blob/5749936352339bdc3705c6d887042f1443e73355/docs/comparison.md)).

Before running, select explicit latency, interruption, throughput, and memory budgets for the target device. Those are acceptance targets, not research findings. Stop when corrected adapters meet those budgets and functional fixtures pass. Allow one correction round for a demonstrated failure, rather than a campaign to maximize every score. If missing session or concurrent-pipeline behavior remains decisive, produce one focused upstream contract proposal or one alternative-runtime pilot. A maintained fork becomes a decision only when the required contract cannot fit an acceptable upstream change. No alternative's throughput, startup, or memory advantage has been established here.
