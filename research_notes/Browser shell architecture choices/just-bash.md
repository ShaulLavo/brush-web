# just-bash APIs, fair evaluation, and browser alternatives

## Can public just-bash APIs provide the same interactive session as Brush?

### Takeaway

The published browser API is a good isolated-script engine with a shared filesystem. It does not expose a complete persistent shell session, incremental terminal output, or a live stdin reader. Those gaps remain in the inspected current source. Some returned scalar state can legitimately be carried into the next call through public options, but that is a partial adapter mode rather than full shell continuity. [Published API](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts), [current API](https://github.com/vercel-labs/just-bash/blob/3ebd1c291462bc6bad3c6df7ebfe563d8799bfd9/packages/just-bash/src/Bash.ts).

### Cited Findings

- Research date is 2026-10-14. npm still reports `just-bash@3.6.0` as latest. Its recorded publication provenance is `7537a260e38648e8998db7a95504102ad80b0194`; inspected upstream HEAD is `3ebd1c291462bc6bad3c6df7ebfe563d8799bfd9`, committed on 2026-10-13. HEAD is five commits ahead of the publication revision. [npm latest](https://registry.npmjs.org/just-bash/latest), [publication attestation](https://registry.npmjs.org/-/npm/v1/attestations/just-bash@3.6.0), [revision comparison](https://github.com/vercel-labs/just-bash/compare/7537a260e38648e8998db7a95504102ad80b0194...3ebd1c291462bc6bad3c6df7ebfe563d8799bfd9).
- README explicitly promises isolated `exec()` shell state and shared filesystem changes. `Bash.execInScope` creates a fresh `InterpreterState`, copies environment, arrays, functions, and options, then constructs a new `Interpreter`. `getCwd()` and `getEnv()` read the instance's initial state rather than the last execution's state. No public session or state snapshot/restore method appears in either reviewed revision. [README](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/README.md#quick-start), [published implementation](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts#L698-L776), [current implementation](https://github.com/vercel-labs/just-bash/blob/3ebd1c291462bc6bad3c6df7ebfe563d8799bfd9/packages/just-bash/src/Bash.ts).
- The return value contains a final `env: Record<string, string>`. Passing that record to the next public `exec(..., {env, cwd})` can carry scalar values and ordinary `PWD`-based cwd. The record lacks array values, function ASTs, shell options, variable attributes, and the interpreter's actual directory as a separate typed field. `PWD` can be unset or assigned by shell code. [Public options and result](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts), [result type](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/types.ts), [state type](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/interpreter/types.ts).
- Important nuance: alias definitions are stored as scalar environment entries by the package's `alias` command. Blindly carrying the public `result.env` also carries that alias data without manually reconstructing its format. Alias expansion still depends on shell options, which are not carried by the result. It is incorrect to claim aliases categorically cannot be transferred through public APIs. [Alias implementation](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/commands/alias/alias.ts), [fresh state/options](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts#L745-L758).
- A bounded local API probe used the installed browser entry inside a Node 26.7 worker, with fixed in-memory files and no native execution. Initial script was `export CARRY=value; array=(one two); f(){ echo function; }; alias hi='echo alias'; cd /tmp; false`. It returned `PWD=/tmp`, `CARRY=value`, and `?=1`. A normal second exec reported `carry: pwd:/home/user status:0` and lacked `f` and `hi`. A second exec with `{env: initial.env, cwd: initial.env.PWD}` reported `carry:value pwd:/tmp status:0`, an empty `array[0]`, no `f`, and the carried alias definition. `bash.getCwd()` remained `/home/user`. This probe confirms API semantics, not browser latency or full interactive compatibility. Its results match the state and alias implementations cited above.
- `ExecOptions.stdin` is a fixed string, with optional text or byte-string interpretation. There is no reader, async iterator, or ReadableStream option. The interpreter's `executeScript` collects statement results in `ExecutionOutputAccumulator`; pipelines execute sequentially and pass each completed stdout string as the next stdin. [Exec options](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts), [script accumulation](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/interpreter/interpreter.ts#L237-L253), [pipeline execution](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/interpreter/pipeline-execution.ts).
- `logger.debug('stdout', ...)` runs in `logResult` after execution and cleanup. It is not a streaming output callback. A bounded probe of `echo first; sleep 0.05; echo last` emitted a single stdout log containing both lines after completion. The `trace` callback publishes timing events such as category, name, duration, and details, not output chunks. [Result logging](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts#L601-L659), [TraceEvent](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/types.ts).
- Cancellation is a public `AbortSignal` option. Statement execution checks `.aborted`; the aggregate execution scope also checks it and a deadline. This supports cooperative cancellation but does not mean a worker can process a queued `postMessage` during an indefinitely replenished microtask chain. The current adapter's SAB-backed signal getter handles that scheduling distinction. [Statement checkpoint](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/interpreter/interpreter.ts#L432-L437), [scope checkpoint](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/execution-scope.ts#L364-L375), [adapter](https://github.com/ShaulLavo/brush-web/blob/b240c0e6b85a53d0ba55291e2f3589bea51e2658/src/baseline.ts).
- The package's CLI shell still awaits `Bash.exec()` and writes the completed strings. Its prompt reads the original `getCwd()`. Its special textual handling of `exit` does not provide an alternate persistent interpreter API. Browser exports omit the internal `Interpreter` and its state types. [CLI source](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/cli/shell.ts), [browser exports](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/browser.ts).

### Inferences

- Keep the existing isolated-script baseline as the stock public API comparison. A separate, explicitly labeled scalar-state adapter could carry `result.env` and ordinary cwd to test a better use of the API. It must report arrays, functions, options, export attributes, status, and `PWD` manipulation as separate acceptance cases. Do not call that adapter a full session.
- A genuine just-bash session would benefit from an upstream API that owns `InterpreterState`, exposes typed stdin/stdout/stderr channels, and creates a fresh cancellation/execution budget for each submitted command. That is an architecture change, not a formatting or batching optimization.
- One permanently running `exec()` loop with a custom input command can retain some interpreter state, but ordinary output still accumulates, the execution deadline/budgets span the loop, and aborting the execution loses its state. Redirecting output into a specially intercepted filesystem path adds another host contract. This composition is a bounded prototype idea, not a demonstrated equivalent session or a recommended production workaround.
- Importing internal interpreter files, mutating private `.state`, or serializing functions by inspecting command text would confuse engine capability with adapter tricks. It would also abandon the supported package export contract.

### Gaps

- I did not build current HEAD or claim that its text-processing speedup applies to this browser demo. No public persistent-session proposal or accepted upstream design was identified in the inspected APIs.
- The local API probe ran in a Node worker with the browser bundle. Browser scheduling conclusions rely on the existing actual-browser fixtures, not on that semantic probe.
- Exhaustive compatibility of carrying `result.env`, especially readonly/export attributes and manipulated `PWD`, remains unproven. The source already establishes that the result is not a complete typed state snapshot.

## How can just-bash be used and measured more fairly before choosing an engine?

### Takeaway

Improve the comparison at the boundary between execution, host work, and presentation before tuning either interpreter. The existing end-to-end data proves useful shell behavior and output timing, but its roughly 47 ms arithmetic/substitution floor cannot rank interpreter CPU speed. Current just-bash HEAD also includes relevant text-allocation improvements that deserve a pinned candidate test rather than an assumed win. [Existing evidence and method](https://github.com/ShaulLavo/brush-web/blob/b240c0e6b85a53d0ba55291e2f3589bea51e2658/docs/commands.md), [upstream optimization commit](https://github.com/vercel-labs/just-bash/commit/864dfe5d4b9cf0447c4eb2002193f2ab2008bd0e).

### Cited Findings

- The comparison uses keyboard input, a standalone submitted-frame marker, one warmup, and five warm trials. It includes Enter delivery, worker transport, rendering, and browser polling. It explicitly identifies Canvas2D and avoids interpreting the result as hardware WebGPU or pure interpreter speed. [Benchmark runner](https://github.com/ShaulLavo/brush-web/blob/b240c0e6b85a53d0ba55291e2f3589bea51e2658/scripts/compare-commands.mjs), [raw samples](https://github.com/ShaulLavo/brush-web/blob/b240c0e6b85a53d0ba55291e2f3589bea51e2658/docs/evidence/command-benchmarks.json).
- The current baseline enables 45 package commands; the installed browser catalog advertises 81. That is an adapter decision, not an inherent just-bash limit. Browser source explicitly excludes `tar`, `yq`, `xan`, `sqlite3`, and Python. The browser entry also warns that `gzip`, `gunzip`, and `zcat` use unsupported Node zlib. Catalog names therefore need individual browser checks rather than blindly enabling every name. [Configured inventory](https://github.com/ShaulLavo/brush-web/blob/b240c0e6b85a53d0ba55291e2f3589bea51e2658/docs/commands.md), [browser exclusions](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/commands/browser-excluded.ts), [browser entry](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/browser.ts).
- The public embedding API supports custom commands, an injected filesystem, a timing trace callback, explicit command selection, execution limits, and defense-in-depth configuration. These are supported places to improve workload matching and attribution without private state changes. [BashOptions](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/Bash.ts), [custom commands](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/README.md#custom-commands), [limits](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/limits.ts).
- Commit `864dfe5...` describes lower allocation in text processing and includes encoding/command allocation changes. The changes are in HEAD but not the pinned publication. The other four commits concern nested-shell environment inheritance, jq index evaluation, redirect-open errors, and `/dev/null`. They do not add persistent-session or streaming APIs. [Five-commit comparison](https://github.com/vercel-labs/just-bash/compare/7537a260e38648e8998db7a95504102ad80b0194...3ebd1c291462bc6bad3c6df7ebfe563d8799bfd9).
- Existing startup/streaming evidence observes Brush's first output before a 0.3 second sleep completes, while stock just-bash returns both lines at completion. That follows the public output contracts rather than terminal renderer quality. [Comparison](https://github.com/ShaulLavo/brush-web/blob/b240c0e6b85a53d0ba55291e2f3589bea51e2658/docs/comparison.md), [script accumulation](https://github.com/vercel-labs/just-bash/blob/7537a260e38648e8998db7a95504102ad80b0194/packages/just-bash/src/interpreter/interpreter.ts#L237-L253).

### Inferences

- A bounded next experiment should have four separately reported measurements: worker execution excluding terminal output, filesystem/utility work, transport/scheduling, and terminal input-to-frame latency. Reuse the same checksum fixtures and browser/hardware disclosures; do not compare Rust `seq` flushing against JavaScript `seq` aggregation as a VM-speed test.
- For execution, add worker-local start/stop timestamps around the same submitted script in stock Brush and stock `Bash.exec`. Keep direct execution timestamps separate from terminal-visible completion. Use arithmetic and command-substitution workloads at 2,000, 20,000, and a bounded 200,000 iterations, retaining the correctness sums. Warm each engine, alternate order, then collect at least 30 samples per chosen workload. Stop after this fixed matrix rather than tuning indefinitely.
- For host work, retain each engine's native filesystem as one case, then add the same narrowly specified host utility operations through public just-bash custom commands and the Brush command host. Record filesystem calls/bytes, allocation or memory where available, and the public just-bash `trace` events. This distinguishes interpreter expansion/dispatch from text processing and storage behavior.
- For scheduler and transport, replay fixed byte payloads and chunk schedules through the shared terminal adapter without executing a shell. Measure main-thread pump/drain cost and submitted-frame timing separately. This is a terminal/adapter experiment, not shell compatibility evidence. Match total bytes, chunk sizes, backpressure limits, and final content.
- For behavior, keep persistent state, live stdin, time to first output, cancellation while executing and waiting, and recovery as pass/fail acceptance. Never compensate for a failed behavior by averaging it into a throughput score.
- A fair just-bash improvement trial can use a verified broader browser command set, injected/shared operation contracts, trace-based attribution, and an explicitly labeled public-env carry adapter. Also build the pinned current HEAD as a separate candidate. Record publication versus HEAD and changed command semantics. Do not silently replace the published baseline or strip limits from only one engine.
- The decision after that matrix should be either keep the measured architecture, open a narrowly scoped session/streaming design discussion, or run one alternative-engine pilot. It should not trigger an open-ended Brush optimization campaign or a permanent fork automatically.

### Gaps

- No worker-local execution timings, allocator-live measurements, or matched host-operation benchmark currently exist in this research. Existing measurements cannot answer which interpreter executes shell ASTs faster.
- Upstream's text-performance claim was not reproduced on this host or in this browser. It is a candidate for measurement, not an established benefit here.
- No GPU failure was observed or researched in this lane. Renderer investigation is not needed to explain the current public just-bash output contract.

## Are other projects credible architecture precedents or browser candidates?

### Takeaway

`mvdan/sh` is a credible alternative design reference because its public interpreter owns reusable state and accepts stream readers/writers plus explicit filesystem and command handlers. It now contains a `js/wasm` stdin adaptation, but the source documents an important cancellation gap. `bash-parser` is a parser rather than an executable shell and cannot replace Brush or just-bash without a new interpreter and host. [mvdan API](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/api.go), [js stdin](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/stdin_js.go), [bash-parser README](https://github.com/vorpaljs/bash-parser/blob/67a05de4238e4fea016677c308ce101070e9c4e8/readme.md).

### Cited Findings

- Reviewed `mvdan/sh` HEAD is `0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7`, dated 2026-10-12. Its README describes a parser, formatter, and interpreter implemented in Go, with configurable interpreter handlers. [Pinned README](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/README.md).
- `interp.Runner.Run` can be called repeatedly and synchronously; omitting `Reset` preserves variables, options, cwd, and functions. `Run` resets execution exit tracking while retaining the runner state. `StdIO` accepts `io.Reader` and separate `io.Writer` instances, which is the right contract for incremental output and live input. [Run and Reset](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/api.go#L972-L980), [incremental Run](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/api.go#L1187-L1246), [StdIO](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/api.go#L731-L765).
- The public `ExecHandler`, `OpenHandler`, `ReadDirHandler2`, `StatHandler`, and related callbacks allow explicit browser command and filesystem hosting. Defaults use OS process/filesystem behavior, so a browser embedding must replace those defaults. The package itself warns that handlers alone do not create a secure sandbox if other capabilities remain available. [Handler API](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/handler.go), [package warning](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/api.go#L1-L21).
- The `js/wasm` implementation uses in-process `io.Pipe` and accepts a reader directly. It reports no terminal and has no read deadlines. Its documented consequence is that cancelling context does not unblock a blocked `read`; the next write does. A browser host must provide an interruptible reader rather than assume stock context cancellation covers stdin. `Interactive(true)` currently enables alias expansion, not a prompt line editor. [js implementation](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/stdin_js.go), [StdIO warning](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/api.go#L743-L750), [Interactive option](https://github.com/mvdan/sh/blob/0e8ea6fccd96b3afdd755e12ff09d88445f6a8e7/interp/api.go#L479-L488).
- Reviewed `bash-parser` HEAD is `67a05de4238e4fea016677c308ce101070e9c4e8`, dated 2024-06-23. Its documented API parses source into an AST. It supplies no execution, session, stream, or command-host contract in that API. [Pinned README](https://github.com/vorpaljs/bash-parser/blob/67a05de4238e4fea016677c308ce101070e9c4e8/readme.md), [commit](https://github.com/vorpaljs/bash-parser/commit/67a05de4238e4fea016677c308ce101070e9c4e8).

### Inferences

- One `mvdan/sh` browser-worker pilot is more informative than comparing parser libraries as though they were shells. Bound it to a reusable runner, a memory filesystem, a fixed command host, live read/write streams, and cancellation while a builtin reads or loops. Reuse Ghostty and the same functional fixtures. Require preservation of cwd, exported values, functions, aliases, and usable prompt state after cancellation.
- Even if the public Go API fits better, it still needs a browser build, host reader cancellation, a line editor, and measurements of startup/memory. It is not a ready-made Ghostty shell replacement demonstrated by this research.
- The useful precedent for just-bash or Brush is the explicit separation of persistent interpreter state, per-command execution context/cancellation, host filesystem and commands, and live byte streams. That contract can guide a focused upstream proposal without committing to a fork or engine switch now.

### Gaps

- No mvdan Go/WASM browser build or performance test was run. Its cancellation recovery, aliases after interruption, startup cost, Go runtime scheduling, and browser filesystem compatibility remain pilot acceptance questions.
- This lane did not survey every JavaScript shell, historical Linux-in-browser emulator, or native Bash port. The small comparison deliberately covers one real reusable interpreter precedent and one commonly confused parser-only project.
