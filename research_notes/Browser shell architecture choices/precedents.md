# Browser shell architecture precedents

Research date: 2026-10-14. This is a source and documentation review, with no installation, browser trial, or performance measurement. No executable third-party code was downloaded. The only retained resource is this note.

## Which existing projects match this milestone?

### Takeaway

Wasmer's WASIX Bash example is the closest precedent for a real shell running in browser workers. v86 and WebVM demonstrate broader native software compatibility by supplying an entire machine or Linux process environment. WebContainers supplies a browser Node.js process runtime. These solve different problems from a reusable shell interpreter.

- Wasmer's inspected shell source specifies a 1 MiB output allowance and streams bytes incrementally through a `TextDecoder` for transcript text. It also writes original byte chunks to the terminal. [source](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/wasmer-sh/src/main.ts#L528)
- Wasmer's terminal resize routes `SIGWINCH` to a waited child. `kill` signals `SIGKILL`, and the implementation explicitly accounts for workers suspended in atomic waits. The latter is emergency process cancellation, not evidence that a Ctrl+C tight loop preserves shell state. [process implementation](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/rust/src/process.rs#L263)
- wasmer.sh documents browser regression coverage for Ctrl+C recovery, typing during a 2 MiB output burst, and worker diagnostics. These are upstream descriptions of tests, not tests run in this research. [stress documentation](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/wasmer-sh/README.md#L303)
- WebVM's own license text distinguishes individual exploration of the public CheerpX deployment from organizational use. It also says downloading a CheerpX build to host elsewhere needs a commercial license. Apache-2.0 on WebVM cannot be treated as a license to fork the engine. [license statement](https://github.com/leaningtech/webvm/blob/7cd36b8d5b32a7532b1af11585d0de26ad92a251/README.md#license)
- v86's current contribution policy does not accept generative-AI-written PRs or issues except case-by-case exceptions. This matters if considering upstream work. [policy](https://github.com/copy/v86/blob/94faf3d6b19ecabc53a4010aaa24252fa6a162e2/Readme.md#generative-ai)

### Inferences

- Wasmer provides useful examples for a terminal-facing byte-stream interface, bounded buffers, worker lifecycle, and TTY ownership. Pulling in its entire sandbox/package/process system would exceed this spike's scope.
- v86 and CheerpX become relevant when the requirement changes to running existing Linux binaries. They do not answer which shell library makes the best interactive browser shell.
- The public WebContainer stream/process API is a useful interface precedent. Its implementation cannot supply a source-level explanation for Brush's current costs.
- The libraries used to render these upstream demos are incidental. Their I/O ideas can be studied without changing the locked Ghostty terminal or Remix 3 workbench.

### Gaps

- No comparable compressed startup payload, warm startup, throughput, memory, or latency measurements were collected. The npm unpacked sizes above describe different packaging boundaries and must not be ranked as runtime performance.
- Guest command inventories depend on image or package selection. This research does not claim these examples all provide the same commands.
- Tight-loop Ctrl+C behavior and session preservation were not exercised in any precedent. A public `kill` method does not prove Ctrl+C semantics.
- CheerpX documentation endpoints returned HTTP 403. The source and README establish chunked output and licensing distinctions, but not internal batching thresholds or interrupt delivery.
- The WebContainer browser-support page labels Firefox beta in its summary and alpha in its detailed section. Treat non-Chromium support as limited, rather than assigning a precise maturity level.

## Does WASM require one browser call for every small shell write?

### Takeaway

No. Separate small writes are a writer/backend decision, and moving them through a browser boundary separately is a second decision. Buffering can group internal writes before that boundary. Chunking only after JavaScript receives each write reduces downstream work but does not remove those original WASM imports.

### Cited findings

- Rust's `BufWriter<W>` keeps data in memory and sends large, infrequent batches to its underlying writer. The official example turns ten byte writes into one underlying call on flush. The documentation requires explicit flush handling to observe errors. [Rust documentation](https://doc.rust-lang.org/std/io/struct.BufWriter.html)
- v86 has a serial adapter that calls the terminal once per byte, and a virtio-console adapter that calls it once per `Uint8Array` chunk. Both live in the same source file. That is direct evidence that granularity can be a transport choice within one WASM-based product. It does not prove any exact speedup. [adapter source](https://github.com/copy/v86/blob/94faf3d6b19ecabc53a4010aaa24252fa6a162e2/src/browser/serial.js#L318)
- WebVM receives an output buffer through `setCustomConsole` and hands a `Uint8Array` to the terminal. The page does not process one JS callback per output character. Its input adapter does loop over code units individually, showing that a project can make different input and output tradeoffs. [output and input source](https://github.com/leaningtech/webvm/blob/7cd36b8d5b32a7532b1af11585d0de26ad92a251/src/lib/WebVM.svelte#L29)
- Wasmer's `bounded_pipe` transports owned byte chunks through a lock-free channel and accounts for total buffered bytes with atomics. Maximum pipe chunk size is 64 KiB. Its reader fills a caller's read buffer from multiple pending chunks before returning. [stream implementation](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/rust/src/stream.rs#L21)
- Wasmer's pipe comment explicitly avoids Tokio `DuplexStream` because its synchronous mutex can cause `Atomics.wait` on the window thread. The chosen pipe returns pending work and wakes writers when capacity is available. [pipe rationale and implementation](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/rust/src/stream.rs#L58)
- WebContainers exposes `ReadableStream<string>` output and documents that a process can emit stream chunks repeatedly. Its public contract does not tie terminal updates to one shell instruction or one character. [running processes](https://webcontainers.io/guides/running-processes)

### Inferences

- The example "number, then newline" is not an architectural reason to abandon Rust. It is a reason to inspect where the unbuffered writer reaches the browser host.
- A wrapper inside Rust can eliminate repeated host calls if all affected output uses that wrapper. Buffering in JavaScript after `fd_write` can only eliminate subsequent copies, notifications, or terminal calls. These changes must be measured separately.
- A timer callback cannot flush a buffer inside a worker that is stuck in synchronous execution. A practical design needs explicit flush points in execution, before blocking input, at prompt transitions, on interrupt/exit, and at bounded size or execution intervals.
- Bulk output, interactive redraws, stderr, pipelines, and file redirections need distinct semantics. A blanket delay on every write would damage prompt latency or redirect behavior. Preserve byte order and flush/error semantics before tuning batch sizes.
- None of the other projects proves that fewer calls alone will make Brush faster than just-bash. Interpreter work, host commands, filesystem algorithms, browser scheduling, and renderer work remain separate costs.

### Gaps

- Whether Brush's existing terminal and open-file abstractions admit a buffering wrapper without patches is for the Brush source audit. These precedents cannot answer that API question.
- We have no isolated measurement of the cost of one WASM-to-JS import on this machine. Calling a small import "terrible" or claiming a permanent severe penalty would be unsupported.
- The existing profiler counts must distinguish upstream builtin output from host utility output. A host-provided `seq` writing numbers individually is an adapter issue, not automatically a Brush interpreter issue.

## What should this imply for optimization and a possible Brush fork?

### Takeaway

First make the comparison represent the same product semantics, then fix measured host and transport waste. Forking Brush is justified only when the needed browser behavior cannot be implemented through its host interfaces or accepted upstream changes.

### Cited findings

- Both Wasmer's browser shell and WebVM leave parsing, expansion, prompt behavior, and ongoing session state to a long-lived guest shell. Their browser UIs primarily transport terminal events. [Wasmer shell architecture](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/wasmer-sh/README.md#L101), [WebVM process and console setup](https://github.com/leaningtech/webvm/blob/7cd36b8d5b32a7532b1af11585d0de26ad92a251/src/lib/WebVM.svelte#L320)
- Wasmer separates finite command capture via `run()` from live stdin/stdout/stderr and lifecycle via `spawn()`. This provides an explicit precedent for comparing batch execution and interactive streaming as different operating modes. [SDK guide](https://github.com/wasmerio/wasmer-sdk/blob/0ba1eadc55daff2f1005e5c44eb5d246199187bd/js/README.md)
- v86's machine model includes CPU translation, hardware, guest kernel, and userland. CheerpX includes CPU translation and a Linux syscall environment. Replacing a shell interpreter with either changes the architecture and the command-compatibility goal. [v86 architecture](https://github.com/copy/v86/blob/94faf3d6b19ecabc53a4010aaa24252fa6a162e2/docs/how-it-works.md), [WebVM architecture](https://github.com/leaningtech/webvm/blob/7cd36b8d5b32a7532b1af11585d0de26ad92a251/README.md#what-is-webvm)

### Inferences

- Use one session contract for the existing Brush and just-bash adapters. Record meaningful differences in live stdin, persistence, cancellation, and output delivery instead of hiding them in one timing total.
- Use three timing boundaries: execution without rendering, execution plus host I/O, and terminal-visible interaction. Compare the same shell fixture and equivalent output semantics at each boundary.
- Start with bounded Rust-side output batches, buffered reads, and amortized filesystem growth where profiles prove waste. These are local design corrections with known mechanisms. Keep a result only if it improves the relevant boundary without failing interactive tests.
- Give just-bash the same attention. Inspect whether its persistent API and incremental hooks avoid reconstructing sessions or retaining all command output. Do not deliberately preserve a weak adapter as the baseline.
- Set a bounded decision checkpoint rather than trying to optimize both "to the max." After making session semantics explicit and removing known quadratic or per-byte adapter work, ask whether one runtime still misses latency, interruption, compatibility, or memory requirements.
- Prefer a small browser backend patch or upstream host-interface improvement over a broad Brush fork. A fork is warranted by a concrete missing abstraction, such as cancellation checks that cannot be injected, or output hooks that cannot be buffered safely. It is not warranted by the implementation language alone.

### Gaps

- The exact acceptance targets for startup, interaction latency, memory, and command compatibility remain product decisions. There is no research-backed universal cutoff for choosing Brush over just-bash.
- The just-bash adapter's source and current APIs are being investigated separately. This note does not claim which state or streaming improvements are possible there.
